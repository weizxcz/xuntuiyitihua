# 草图图像「感知层」设计方案：图像 → 结构化草图规格（SketchSpec）

> 本文是 `sketch-transpile-verify-design.md` 的**前置补充**，专门解决其当前缺失、也是业务最痛的一环：**草图图片 → 结构化草图规格（SketchSpec）**。
> 下游的 SketchSpec / Transpiler / `verify_sketch` 验证闭环**直接复用**现有设计，本文不重复。
> 调研/撰写时间：2026-07-21

---

## 0. 对标澄清：CADSmith 做了什么、没做什么（避免误对标）

经核对论文原文（arXiv:2603.26512），CADSmith 的真实做法是：

- **输入模态 = 纯自然语言文本**，不是草图图片。Planner 把 NL 解析成 JSON 设计计划，全流程基于文本。
- **"程序化几何验证" = OpenCASCADE(OCCT) 内核量生成的 B-rep**（体积、包围盒、质心、面/边/顶点数、实体是否水密）；数值不对直接判失败。
- **VLM Judge = 看渲染出的三视图**（VTK 渲染的等距/后视/前侧轮廓图），数特征、比对尺寸、抓"数值对但形状错"的虚假收敛。
- 双嵌套循环 + RAG 查 API 文档 + 不微调。

**结论**：CADSmith **不使用 SAM / Hough / OCR 去识别草图图像**，因为它根本不从图像起步。因此——

> **CV/几何感知层是本项目的增量贡献，而非 CADSmith 的既有能力。** 我们的差异化定位是：CADSmith 解决「NL → CAD」，我们解决「草图图片 → 结构化几何 → CAD」，输入模态不同，必须在 CADSmith 范式前补一个"感知前端"。

---

## 1. 问题定义与根因

### 1.1 当前痛点
用户上传草图图片，要求"照图绘制"。现有 `SOUL.md` 的流程是 `view_image` 看一眼 → LLM 直接生成 NCTI 脚本。问题正出在你描述的现象：

> LLM 识别不出具体的结构和尺寸，会有误差，且用自然语言描述不出来。

### 1.2 根因（关键认识）
把"**图像理解**"和"**数值精度**"两件事都压在 VLM 的 language head 上，而**自然语言是 lossy（有损）的表示**：
- VLM 看像素 → 用文字描述"大概 50 左右" → 精度在语言化那一刻就丢了；
- 复杂结构（多圆相切、对称阵列、隐藏线）在语言描述里进一步塌缩；
- 一旦要求"用自然语言描述"，误差无法被量化、无法被校验。

### 1.3 解决思路（一句话）
**不让 LLM/VLM 当"数值真值来源"。让 CV/几何算法当数值真值来源（精确到像素→毫米），让 LLM/VLM 只当编排者（决定调哪个工具、如何消歧、何时澄清），且最终产出必须是结构化 SketchSpec，而不是自然语言。**

这样精度由确定性算法保证，语义/消歧由 LLM 兜底，误差在验证闭环里被收敛。

## 2. 总体架构：三阶段流水线

```
草图图片
   │
   ▼
[Stage 1 感知 Perception]  ── 确定性 CV/几何 + OCR ──► 原始图元 + 像素级测量值
   │                          （VLM 仅兜底语义/手绘）
   ▼
[Stage 2 结构化 Structuring] ── 尺度标定(px→mm) + 约束推断 + 组装 ──► SketchSpec(JSON)
   │
   ▼
[Stage 3 验证闭环 Verify]   ── 复用现有 Transpiler + verify_sketch ──► NCTI 求解
   │                                      │
   │   冲突/退化/尺寸不符 ◄──────────────┘ 回灌感知层重测
   ▼
   合格 SketchSpec → 生成内核脚本
```

**角色分工原则**：
- **CV/几何算法 = 数值真值来源**（坐标、长度、半径、角度、像素测量）。
- **OCR = 尺寸标注真值来源**（把图上的 "50"、"Φ20"、"R10" 读出来）。
- **VLM/LLM = 编排者与语义兜底**（选工具、消歧、处理严重手绘/遮挡、判断对称/阵列等高级意图），**且输出必须落入结构化字段，禁止自由文本描述几何**。

## 3. Stage 1 感知层详细设计

### 3.1 图像预处理
- 灰度化 → 二值化（自适应阈值/Otsu）→ 去噪（高斯/中值滤波）→ 形态学闭运算连接断线。
- **图层分离**：草图通常含"几何线"（粗、连续）与"尺寸标注/文字"（细线+箭头+字符）。用连通域面积/长宽比/是否含字符，把标注层与几何层分开处理，避免标注线被误检为几何。

### 3.2 图元检测（确定性 CV，输出像素级参数）
| 图元 | 算法 | 输出 |
|------|------|------|
| 直线/线段 | Canny + HoughLinesP | 端点像素坐标 (x1,y1,x2,y2) |
| 圆 | HoughCircles / 轮廓+圆拟合 | 圆心像素、半径像素 |
| 圆弧 | 轮廓分段 + 圆弧拟合 | 圆心、半径、起止角 |
| 椭圆 | 轮廓 + `cv2.fitEllipse` | 中心、长短轴向量、起止角 |
| 矩形/多边形 | 轮廓 + `approxPolyDP` 角点 | 顶点序列 |
| 样条 | 轮廓等距采样 | 控制点序列 |

> 全部输出**像素坐标**，不在此阶段猜毫米数（尺度见 4.1）。

### 3.3 尺寸与标注识别（OCR + 几何关联）
- **OCR**：用 PaddleOCR / Tesseract 识别尺寸数字与符号（Φ、R、°、公差）。
- **关联（关键）**：尺寸标注的引出线/箭头指向哪个图元，就把数字挂到该图元上：
  - 线性尺寸 → 对应线段的 `length`；
  - 直径/半径标注 → 对应圆/圆弧的 `radius`；
  - 角度标注 → 两线夹角。
- 这一步**替代了 VLM 猜数字**，是尺寸精度的主要来源。

### 3.4 视觉语义理解（VLM 的有限职责）
VLM **不负责出数值**，只用于：
- 区分草图元素语义：哪条是中心线/构造线、哪条是轮廓、哪些是参考尺寸；
- 处理严重手绘、线条断裂、遮挡等 CV 失效场景；
- 判断对称、阵列、镜像等高级意图。
- **硬约束**：VLM 的输出也必须映射到结构化字段（如 `"role":"centerline"`、`"pattern":"mirror"`），不允许输出自由文本几何描述。

## 4. Stage 2 结构化：尺度标定 + 约束推断 + 组装

### 4.1 尺度标定（最关键！图像没有内禀尺度）
草图图片本身不带单位，必须把像素换算成毫米：

- **方式 1（首选）**：利用图中已有尺寸标注——OCR 读出数字（如 "50"），同时 CV 量出该标注对应的像素长度 → 得到 `px/mm` 比例。
- **方式 2**：用户显式提供比例或参考长度（如"图上这条是 100mm"）。
- **方式 3（兜底）**：若完全无标注且无参考，归一化到视图包围盒，并在 SketchSpec 中标记 `"scale":"uncalibrated"`，触发 `ClarificationMiddleware` 向用户澄清比例。

> 所有像素坐标 → 乘以比例 → 毫米坐标，写入 SketchSpec。

### 4.2 约束推断（几何推导，不是 LLM 猜）
| 约束 | 推断依据（可量化） |
|------|------|
| 平行 / 垂直 | 两线段角度差接近 0° / 90°（带阈值） |
| 相切 | 圆心到线段距离 ≈ 半径 |
| 相等 | 两长度/半径测量值相近（带阈值） |
| 重合 | 两端点像素距离 ≈ 0 |
| 对称 / 阵列 | 中点重合或等间距规律 |

这些全部可由测量值**确定性推导**，输出到 `SketchSpec.constraints`，避免 LLM 凭感觉加约束。

### 4.3 组装 SketchSpec
直接复用 `sketch-transpile-verify-design.md` 第 4.1 节的 JSON Schema（图元 id 稳定引用、13 几何 + 12 约束类型一一映射）。感知层产物即一份完整的 SketchSpec。

## 5. Stage 3 验证闭环（复用现有，仅扩展回灌）

- `SketchSpec → Transpiler → NCTI RunSolve`（转译器确定性生成，天然规避语法/API 错误）。
- `verify_sketch` 读取 DOF / 约束冲突 / 退化几何（依赖内核团队冻结的 B 类接口，见现有文档 5.1 阻塞项）。
- **回灌区分根因**：
  - 若"约束冲突/尺寸与 OCR 不符" → 可能是**感知测错**（像素测量偏差）→ 回 Stage 1 重测该图元；
  - 或**约束推断错**（阈值过严/过松）→ 放宽阈值重新推断；
  - 或**尺度标定错** → 重新标定比例。
- 有界重试（如 ≤3 轮），与 CADSmith 外循环思想同构，只是反馈源从 B-rep 换成草图几何。

## 7. 为什么不直接让 VLM 出 SketchSpec / 出代码

- **数值精度**：VLM 的 language head 对坐标是近似的（正是你的痛点）；确定性 CV 量的是像素，精度由图像分辨率决定，远高于语言描述。
- **微调路线（CAD-Coder 等）有先例但代价高**：需标注数据、权重随内核演进过期；且即便微调，数值精度仍不及"CV 量像素 + 标定"。
- **本方案更优**：CV 出数值真值 + LLM 出编排与兜底，把"下限"用架构手段拉起，不依赖训练数据。

## 8. 实施路线与度量

### 8.1 分阶段（性价比递增）
1. **M0 最小可用**：尺度标定（方式1）+ 直线/圆检测 + OCR 读尺寸 → 简单轴类/板类草图出 SketchSpec。
2. **M1 约束闭环**：约束推断 + verify_sketch 回灌重测。
3. **M2 鲁棒与兜底**：VLM 处理手绘/遮挡；尺度缺失走澄清；对称/阵列识别。
4. **M3（仅若 M0–M2 后仍卡）**：才考虑微调"图像→SketchSpec"的 VLM，用合成数据启动。

### 8.2 度量指标
| 层 | 指标 |
|----|------|
| 感知 | 图元检测 F1、尺寸 MAE（mm，与真值比）、约束 F1（参考 Sketch2CAD） |
| 转译 | Spec→脚本 一次通过率 |
| 验证 | 过求解器一次通过率（pass@1） |
| 业务 | 端到端任务成功率、人工返工率 |

## 9. 风险与开放问题

- **手绘噪声 / 重叠线 / 标注遮挡**：CV 失效处依赖 VLM 兜底，需结构化约束防止幻觉。
- **尺度标定失败**：无标注无参考时只能澄清，无法凭空定标。
- **VLM 幻觉**：用"结构化输出 + 几何校验回灌"双重兜底，不让其数值进入真值链。
- **前置阻塞**：验证闭环仍依赖内核团队冻结 B 类接口（DOF/冲突/退化查询），见现有文档 5.1；感知层本身不依赖该接口，可先独立推进 M0。

## 10. Related Work / 参考

> 本节汇总与"草图图像 → 结构化几何"相关的开源 agent / 论文，并标注**每篇可借鉴的点**，便于方案答辩与实现时引用。调研时间：2026-07-21。

### 10.1 经典 CV 路线（Hough + 规则推理）—— 最贴本方案 Stage 1 + 2.2
- **`sketch-to-constraint`（PraneetBala, GitHub 2026, 开源）** https://github.com/PraneetBala/sketch-to-constraint
  - 做法：图像二值化 + Canny 边缘检测 + **概率霍夫变换提取线段** → **基于极坐标的规则几何推理引擎**，按线段角度差判平行(≈0°/180°)/垂直(≈90°)，彩色叠加约束；无 OCR、无深度学习，轻量可解释。
  - **可借鉴**：几乎就是本项目 Stage 1（Hough 提线）+ Stage 2.2（约束几何推导）的现成开源实现，**M0 基线可直接 fork 改造为 SketchSpec 输出**。
- **DAVINCI（BMVC 2024, 卢森堡 SnT + Artec 3D）** https://arxiv.org/abs/2410.22857
  - 做法：二值光栅草图 → 单阶段 Transformer（U-Net 骨干 + 编码解码）联合推断**基元 + 约束**，输出"草图图" `G=(基元, 约束)`。学习型而非经典 CV。
  - **可借鉴**：证明"图像 → 结构化基元+约束"是学界公认的表示目标，为 **SketchSpec 的设计提供学界背书**；其基元量化/约束无向边表示可参考。
- **PICASSO（WACV 2025, SnT）** https://arxiv.org/abs/2407.13394
  - 做法：手绘/精确草图 → **参数化基元**（渲染自监督），目标一致：图像 → 可导入 CAD 的参数化图元。
  - **可借鉴**：手绘噪声鲁棒性思路；渲染自监督可缓解标注数据稀缺。

### 10.2 混合架构（VLM 理解 + 传统 CV 保几何）—— 支撑设计铁律
- **《让大模型读懂 CAD 工程图纸：从"看图"到"用图"的技术跃迁》（搜狐/智绘工软, 2026-06）** https://www.sohu.com/a/1033577577_122155911
  - 核心论点：**纯 VLM 不够**（幻觉、像素级精度缺失、证据不可追溯）；最优是**分层混合架构**——VLM 管上下文/复杂标注，传统视觉/规则管定位、几何关系、格式约束；点名 **FlowExtract 实验证明"检测‑OCR‑连线追踪"流水线优于端到端 VLM**。
  - **可借鉴**：直接支撑本文"CV/几何出数值真值、LLM/VLM 只编排"的铁律；四层认知框架（感知→几何符号→拓扑→语义）可作方案分层依据。
- **Drawing2CAD（2025）** https://arxiv.org/html/2508.18733v1
  - 做法：矢量 PDF/CAD 导出图 → 几何命令序列（画直线→偏移→倒角→标注），生成可编辑参数化模型。
  - **可借鉴**：混合思路代表；矢量图作为输入优于栅格的论点（本项目若用户能提供矢量图可走此捷径）。
- **Hybrid DL + Rule-based 建筑图矢量化（MDPI 2026）** https://www.mdpi.com/2075-5309/16/5/1043 ；**Automated Parsing of Engineering Drawings（arXiv:2505.01530, 2025）** https://arxiv.org/abs/2505.01530
  - **可借鉴**：混合 DL + 规则生成可编辑 CAD 矢量图，验证"混合"路线的工程可行性。

### 10.3 闭环 Agent / 沙盒验证 —— 支撑 Stage 3
- **IterCAD（arXiv:2606.13368, 2026）** https://arxiv.org/abs/2606.13368
  - 做法：多模态 agent + **可执行 CAD 沙盒**，闭环多轮 `Drawing-to-Code / Text-to-Code / Interactive Editing`，用**几何感知强化学习 + 可行前缀掩码**提升代码可执行性与几何保真度。
  - **可借鉴**：与本文 `verify_sketch` 回灌闭环高度同构，可作 **Stage 3 的参考架构**；CD-TR 评估指标可借鉴。
- **CAD-Assistant（arXiv:2412.13810, 2024）** https://arxiv.org/abs/2412.13810（tool-augmented VLLM 通用 CAD agent）；**ScadLM（GitHub, 开源）** https://github.com/KrishKrosh/ScadLM（OpenSCAD agentic CAD）；**agentcad（2026）** https://www.producthunt.com/products/agentcad（写脚本后自检）
  - **可借鉴**：agent 编排与"自检"模式；但起点多为 NL/矢量图，非栅格草图。

### 10.4 端到端 VLM（作为"不该照搬"的对照）
- **CadVLM（ECCV 2024, Autodesk）** https://arxiv.org/abs/2409.17457 ；**GenCAD（MIT, 2026）** ；**CAD-MLLM（2025）** https://cad-mllm.github.io/
  - **可借鉴 / 警示**：端到端 VLM 出 CAD 是精度问题的来源（正是本文要规避的），仅作能力上限对照，不照搬其"图像直接出几何"的路线。

### 10.5 工业界 / 经典
- **Raster2CAD / BeesAI**（商业 AI 栅格转 CAD）：证明"图像→可编辑 CAD"的市场需求与可行性。
- **Deep Vectorization of Technical Drawings（arXiv:2003.05471, 2020）** https://arxiv.org/abs/2003.05471 ：技术图纸矢量化的经典方法。
- **Sketch2CAD（SIGGRAPH Asia 2020）** https://github.com/Enigma-li/Sketch2CAD ：手绘草图→可编辑 CAD（序列建模+分割+几何优化）。
- **DeepCAD（2020）** https://github.com/ChrisWu1997/DeepCAD ：178k CAD 构造序列数据集，可用于 M3 合成训练数据。

### 10.6 工具链
- **OpenCV**：直线/圆/椭圆检测、轮廓拟合（`HoughLinesP` / `HoughCircles` / `fitEllipse` / `approxPolyDP`）。
- **PaddleOCR / Tesseract**：尺寸标注数字与符号（Φ、R、°、公差）识别。

### 10.7 关键结论（贡献点）
现有 agent（CADSmith / IterCAD / ScadLM / CAD-Assistant）多从 **NL 或矢量图**起步，**"栅格草图 → CV 感知 → 结构化规格 → 内核验证闭环"这种组合式方案尚无开源实现**，是本项目相对标杆的**差异化贡献点**。
