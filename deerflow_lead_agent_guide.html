01整体架构与定位

DeerFlow 的 Lead Agent 是一个基于 LangGraph + LangChain 的 ReAct 风格 Agent。它不再是手写 while 循环， 而是用 LangChain 的 create_agent 预构建 ReAct 图，并通过 LangChain 的 AgentMiddleware 机制把"横切关注点" （总结、标题、记忆、待办、澄清、图片查看等）以中间件链的方式注入到模型调用前后。

核心分层（从外到内）：
1. HTTP 网关（FastAPI，app/gateway/routers/thread_runs.py）—— 接收 Run 请求、鉴权、起 Run、把 Graph 事件转成 SSE。
2. RunManager / StreamBridge（packages/harness/deerflow/runtime/）—— Run 元数据管理 + 事件总线，解耦生产者（Agent worker）与消费者（SSE endpoint）。
3. Lead Agent 图（packages/harness/deerflow/agents/lead_agent/agent.py）—— create_agent(...) 构建的 ReAct 图，挂中间件、工具、system prompt、state_schema=ThreadState。
4. Middleware 链（packages/harness/deerflow/agents/middlewares/，26 个文件）—— 包裹模型调用的前置/后置钩子。
5. Tools & Model —— 工具集（搜索、代码执行、浏览器、文件、子代理等）与 LLM（create_chat_model）。

async def stream_run(thread_id, body: RunCreateRequest, request):
    bridge   = get_stream_bridge(request)
    run_mgr  = get_run_manager(request)
    record   = await start_run(body, thread_id, request)      # 创建 RunRecord + 解析 context → RunnableConfig
    return StreamingResponse(
        sse_consumer(bridge, record, request, run_mgr),  # 消费 StreamBridge 事件 → SSE
        media_type="text/event-stream",
        headers={"Content-Location": f"/api/threads/{thread_id}/runs/{record.run_id}"},
    )
关键设计：网关并不"直接跑 Agent"。它调用 start_run(...) 把 Run 交给后台 worker（生产者）， worker 把 Graph 产生的事件 publish 到 StreamBridge；sse_consumer 作为消费者订阅同一 run_id 的事件流。 这实现了 生产者/消费者解耦，并天然支持多端 join 同一 Run、断线重连（Last-Event-ID）。

03ThreadState：Graph 的状态（Schema）

Graph 的 state 用 ThreadState（继承 LangChain AgentState）定义，文件 packages/harness/deerflow/agents/thread_state.py:111。它决定了中间件与节点能读写哪些字段：

class ThreadState(AgentState):
    sandbox:        SandboxStateField            # 沙箱 id（有 merge reducer，幂等写）
    thread_data:    NotRequired[ThreadDataState|None]  # workspace / uploads / outputs 路径
    title:          NotRequired[str|None]        # 会话标题（TitleMiddleware 写）
    artifacts:      Annotated[list[str], merge_artifacts]        # 产出物（去重合并）
    todos:          Annotated[list|None, merge_todos]            # 待办（TodoMiddleware 写）
    uploaded_files: NotRequired[list[dict]|None]
    viewed_images:  Annotated[dict[str, ViewedImageData], merge_viewed_images] # 图片(base64)
    promoted:       Annotated[PromotedTools|None, merge_promoted] # 延迟工具提升
Reducer 的含义（很重要）：LangGraph state 在多节点并发更新时靠 reducer 合并。
  • merge_artifacts：列表追加 + 去重（保留顺序）。
  • merge_viewed_images：字典合并；空 {} 表示清空（中间件处理完图片后可清掉，避免回灌给模型）。
  • merge_todos：最后一次非 None 的写覆盖（None 表示"本节点没动"，保留旧值）。
  • merge_sandbox：幂等，多个沙箱工具同一 step 写同一 id 才允许；冲突则报错。
AgentState 本身已带 messages: Annotated[list[BaseMessage], add_messages]，这是主对话历史通道。

8 ViewImageMiddleware

中间件触发钩子对照表（before_agent / before_model / wrap_model_call）

上一节的速查表只讲了"中间件干什么"，这一节讲清"中间件在 ReAct 循环的哪个钩子被触发"。 理解这一点很关键：同一个中间件链，不同中间件挂的钩子不同，触发时机也不同——有的在整个 Agent 循环启动前只跑一次，有的在每轮模型调用前都跑，有的直接改写发给模型的请求 payload。

三个钩子的语义区分（来自 LangChain AgentMiddleware）：
• before_agent(state, runtime)：整个 ReAct 循环开始前触发一次（每轮 Run 一次）。适合"准备性"工作，如注入日期/记忆。
• before_model(state, runtime)：每一轮 LLM 推理之前触发（循环里可能跑很多次）。适合"上下文裁剪/压缩/工具过滤"等需要每轮判断的工作。
• after_model(state, runtime, result)：每轮 LLM 推理之后、工具执行之前触发。适合"读模型输出、生成标题/todo、反问澄清"。
• wrap_model_call(fn, ...)：包裹整次模型调用，能直接改写 request（system_message / messages）和 response。适合"请求级格式调整"，且不修改持久化 state。
注意：before_agent / before_model / after_model 的返回值会写回 state；wrap_model_call 只在请求 payload 上做手脚，不动 checkpoint。

2. 关键观察与易混点

① 两类"准备型"钩子的区别

DynamicContextMiddleware 用 before_agent——它只在 Run 循环前注入一次，且刻意冻结为前缀缓存（同天不再动），目的是命中 LLM 的前缀缓存、省 token。 而 SummarizationMiddleware 用 before_model——它每轮都要重新算 token 判断是否该压。两者的"频率"差异正是性能取舍的结果。

② SystemMessage 合并在 wrap 层，不动 state

SystemMessageCoalescingMiddleware 挂的是 wrap_model_call，只在"发给模型的请求"上合并，不写回持久化 state。 所以负责扫历史的其它中间件（记忆、摘要）仍能按原始 marker 正常工作——这也是它和 DynamicContextMiddleware（后者改 state）的本质区别。

③ 熔断类都挂 before/after_agent

TokenBudgetMiddleware、LoopDetectionMiddleware 把检查放在 before_agent，保证"循环根本启动前"就判断是否放行；after_agent 再兜底统计。它们不进 before_model 是因为不需要每轮细粒度判断。

④ Clarification 为何永远最后

列表最后追加，因此 after_model 逆序执行时它最先跑——保证"反问澄清"优先于标题、todo 等其它后处理。这体现"挂最后"是为了控制逆序优先级。

一句话记忆： before_agent = 循环前准备（日期/记忆/熔断判门）； before_model = 每轮裁剪（压缩/工具过滤/子agent/视觉）； after_model = 每轮读输出（标题/todo/澄清/安全）； wrap_model_call = 请求级格式改写（合并 SystemMessage / 截断工具输出），且不落盘 state。

06中间件的"包裹"调用顺序（本/逆序）

LangChain 的 AgentMiddleware 把每个中间件看成"包裹"模型调用的一层。每轮模型调用时：

  • before_model（前缀处理）：按列表正序由外到内执行（#1 → #15）。
  • 调用 LLM。
  • after_model（后缀处理）：按列表逆序由内到外执行（#15 → #1）。
before #1 DynamicContext → #2 Skill → ... → #14 Safety → #15 Clarification [外层先] │ ▼ ★ LLM CALL ★ （模型产出 AIMessage / ToolCall） │ after #15 Clarification → #14 Safety → ... → #2 Skill → #1 DynamicContext [内层先]
钩子方法（你能在源码看到的）：
  • before_model(state, runtime) → dict | None：在 LLM 调用前修改 messages / 注入上下文。
  • after_model(state, runtime) → dict | None：在 LLM 返回后写回 state（如 title、todos）。
  • 异步版 abefore_model / aafter_model。
  • 部分中间件还有更细的钩子，如 Summarization 的 before_summarization hook、ToolErrorHandling 的 before_model 转换工具异常为 ToolMessage。
例如 TitleMiddleware.after_model（title_middleware.py:188）仅在满足"首轮对话已完成且无标题"时生成标题： 
# title_middleware.py

# _should_generate_title: 有 >=1 条 human + >=1 条 ai 且 state 还没 title

07核心 ReAct 循环与模型调用

create_agent（LangChain 预构建）内部维护标准 ReAct 循环：

1

接收输入

Graph 输入 {messages:[HumanMessage(...)]}，与 checkpoint 中的历史合并。
2

各中间件 before_model

依次注入上下文、激活 skill、压缩历史、注入待办工具、合并 SystemMessage 等。
3

LLM 推理

模型基于 messages + tools 产出 AIMessageChunk（流式）或 AIMessage（带 tool_calls）。思考模型会先吐 <think> 段（UI 可隐藏）。
4

各中间件 after_model

逆序执行：Clarification 拦截反问、Safety 清 tool_calls、Title 写标题、Memory 排队……
5

若有 tool_calls → 执行工具

LangGraph 把工具结果作为 ToolMessage 追加，回到步骤 2（LoopDetection / TokenBudget 在此兜底）。
6

若没有 tool_calls → 结束

产出最终 AI 回复，Graph 进入 END，StreamBridge 发 end 事件。
LoopDetection / TokenBudget / SafetyFinishReason 都作用在"模型决定调工具"这一刻： LoopDetection 打断重复调用、TokenBudget 超预算强制终止、SafetyFinishReason 在供应商安全终止响应时把 tool_calls 清空，避免后续误执行。

10出参详解（SSE 事件流）

出参是 SSE（Server-Sent Events），由 StreamBridge（runtime/stream_bridge/base.py）统一承载。 生产者 worker 调 bridge.publish(run_id, event, data)，消费者 sse_consumer 用 bridge.subscribe(run_id) 读事件转成 SSE。

# runtime/stream_bridge/base.py:16
@dataclass
class StreamEvent:
    id:   str    # 单调递增，用作 SSE "id:" → 支持 Last-Event-ID 重连
    event: str   # SSE 事件名：metadata / updates / events / error / end ...
    data: Any    # JSON 可序列化负载

SSE 报文格式（对齐 LangGraph Platform，前端 useStream 直接消费）：

event: metadata
id: 1
data: {"run_id":"...", "thread_id":"..."}

event: messages          # stream_mode=messages：逐 token 的 AI 输出
data: {"content":"你"}

event: events            # 自定义业务事件（phase / plan / title / tool_call / artifact...）
data: {"type":"title", "title":"如何做X"}

event: updates           # stream_mode=updates：节点/中间件回写的 state 增量
data: {"title":"如何做X", "todos":[...]}

event: end
data: {"type":"end"}
事件名含义典型 data
metadataRun 元信息（run_id、thread_id）Run 元数据
messagesLLM 流式文本增量增量 AIMessageChunk
eventsDeerFlow 自定义业务事件phase / plan / title / artifact / tool_call 等
updatesGraph state 增量（中间件/节点写回）如 title、todos、artifacts
error运行期错误错误信息
end流结束（END_SENTINEL 映射）{"type":"end"}
HEARTBEAT / END 哨兵：StreamBridge 定义 HEARTBEAT_SENTINEL（空闲 15s 发心跳保活）和 END_SENTINEL（生产者 publish_end 后发出）。 sse_consumer 把这两个 sentinel 翻译成 SSE 的 event: __heartbeat__ 与 event: end。
隐藏/控制消息：网关在序列化前会过滤 _is_hidden_or_control_message 的消息（type=remove、name=summary、带 hide_from_ui 的消息），保证 UI 不会看到摘要占位、内部控制消息等。

11一次完整请求的端到端时序

用户/前端 ──POST /runs/stream {input, context:{model,thinking,plan}}──▶ 网关
   │                                                                   │
   │                                                          start_run()
   │                                                          context → RunnableConfig
   │                                                          创建 RunRecord(thread_id)
   │                                                                   │
   │                                          ┌────────────────────────┴───────────────┐
   │                                          │ 后台 Worker（生产者）                          │
   │                                          │  make_lead_agent(config)                │
   │                                          │   └ build_middlewares() → 中间件链       │
   │                                          │  graph.astream(input, config,           │
   │                                          │        stream_mode=[messages,events,..])│
   │                                          │                                         │
   │                                          │   ReAct loop:                           │
   │                                          │    before_mw(#1→#15) → LLM →            │
   │                                          │    after_mw(#15→#1, 写 title/todos/...)  │
   │                                          │    → 执行 tools → 回到 loop             │
   │                                          │    → END                                │
   │                                          │                                         │
   │                                          │   bridge.publish(run_id, event, data)   │
   │                                          └────────────────────────┬───────────────┘
   │                                                                   │
   │                              StreamBridge（事件总线） ◀──────────────┘
   │                                                                   │
SSE 流 ◀── sse_consumer 订阅 run_id ───────────────────────────────────┘
   event: metadata → messages(token) → events(plan/title) →
   updates(title/todos) → end
一句话总结全流程：前端用 RunCreateRequest（含 context）发起 SSE Run；网关把 context 解析进 RunnableConfig 并起后台 Worker；Worker 用 create_agent 构建带 ThreadState 与完整中间件链的 ReAct 图； 每轮模型调用被 15 个中间件按"正序 before / 逆序 after"包裹；模型产出的 token、业务事件、state 增量都被 StreamBridge.publish 出去，经 sse_consumer 转成 SSE 回给前端；无 tool_calls 时进入 END，发 end 事件。
