## 二、近期项目深挖：Sketch-Modeling-Agent

### 2.1 项目背景

工业 CAD 草图建模依赖 NCTI 闭源 SDK，工程师要写大量 Python 脚本（`SketchWorkPlane`、几何、约束）。LLM 能写代码，但直接让主对话生成脚本会遇到三类问题：

1. **长脚本污染主上下文**——千行级 tool 输出挤掉用户意图；
2. **闭源 API 幻觉**——模型捏造不存在的 `skt.AddXxx()`；
3. **多轮续编丢几何**——整文件重写覆盖已有变量和约束。

### 2.2 系统设计（怎么拆）

```
用户 → 主 Agent（编排 + 7+ 工具）
              ↓ cad_agent Tool
         子 Agent（独立 messages + 白名单 3 工具）
              ↓ read / write_file / edit_file
         output/<session_id>/*.py  ← Plan B「文件即状态」
```

| 模块 | 职责 | 源码 |
|------|------|------|
| `Agent` | LLM ↔ Tool 循环，并行 tool_calls | `corecoder/agent.py` |
| `SkillAgentTool` | 六阶段 spawn 子 Agent | `corecoder/tools/skill_agent.py` |
| `CADAgentTool` | NCTI 专责 + `current_file` 续编 | `corecoder/tools/cad_agent.py` |
| `ContextManager` | 50%/70%/90% 三层压缩 | `corecoder/context.py` |
| `session.py` | JSON 持久化 messages，断点续聊 | `corecoder/session.py` |

**六阶段流水线**（新增 CAD 能力只加 `SKILL.md`，主循环零改动）：

`[A] load skill → [B] select refs → [C] build prompt → [D] prepare task → [E] build tools → [F] spawn + run`

### 2.3 挑战点与卡点

| 挑战 | 卡点 | 我的做法 |
|------|------|----------|
| 子 Agent 结果主 Agent 反复 spawn | 曾截断子 Agent 返回为 120 字，主 Agent 以为丢结果 | 改回完整返回 + 结构化 `[产出文件] path`（`skill_agent.py:195`） |
| 续编丢代码 | `write_file` 整文件覆盖 | Plan B：`current_file` 透传 → 先 `read_file` 再 `edit_file` 唯一定点改 |
| 工具全集幻觉 | 闭源 API 无公开语料 | `cad-sketch` 白名单仅 read/write/edit + `<api_index>` 全量合法接口 |
| 多轮 token 爆炸 | 工具输出 + 历史对话 | 三层压缩：snip → LLM 摘要 → hard collapse |
| 多 tool 延迟 | 一轮多个 tool_calls 串行 | `ThreadPoolExecutor` 并行独立工具 |

### 2.4 优化效果（诚实表述）

- 主对话**不再承载**完整 NCTI 脚本历史，续编靠文件路径而非 inline 代码；
- 子 Agent 工具从 7+ 收敛到 3，spawn 工具从子 Agent 剥离防递归（`_AGENT_SPAWN_TOOLS`）；
- 端到端多轮草图任务可跑满 50 轮子 Agent 轮次而不触顶主上下文；
- **【建议补充真实数据】**：脚本一次通过率、压缩前后 token 数、照图绘制准确率。

### 2.5 和 CAD-Agent-Education（LangGraph 版）的关系

早期用 LangGraph + `soul.md`/`SKILL.md` 验证配置驱动扩能、动态工具过滤、4 段式摘要压缩。后迁移到 CoreCAX 轻量循环，用 `SkillAgentTool` 统一子 Agent 流水线，更适合闭源 CAD 长脚本场景。

## 三、Agent 知识问答

### Q1. 什么是反思机制（Reflection）？如何提升任务执行成功率？

**定义**：Agent 在行动后**审视结果与目标差距**，再决定重试、改计划或向用户澄清——不是单次「调工具 → 结束」。

**常见实现**：

1. **显式反思轮**：工具返回后追加一轮 prompt——「目标是否达成？若否，差在哪？」
2. **结构化自检**：要求模型输出 `status / error / next_step`（类似 ReAct + Critique）
3. **规则 + LLM**：先规则校验（JSON Schema、脚本能否 import），失败再把错误喂回模型

**我在项目里的对应实践**（虽没单独叫 Reflection）：

- **CAD 子 Agent**：`<output_discipline>` 强制一句话汇报产出文件；`MAX_ROUNDS_REACHED` 明确返回「未完成」而非假装成功（`agent.py:23`）；
- **FindJobs**：JSON Schema + 正则解析评分，格式不对可重试一轮；
- **续编**：`read_file` → `edit_file` 前先读现状，等价于「执行前核对状态」。

**提升成功率的关键**：

- 缩小单次动作粒度（edit 而非 rewrite）；
- 工具返回带**可行动错误信息**（`Error: bad arguments...`）；
- 白名单约束减少无效工具调用；
- 子 Agent 隔离，失败不污染主规划上下文。

### Q2. 多 Agent 常见架构？去中心化调度与自治的实现、优缺点、适用场景

**常见架构**：

| 架构 | 调度方式 | 特点 |
|------|----------|------|
| **主从（Orchestrator）** | 中心 Agent 拆任务、派 Sub-agent | 可控、易追溯；中心压力大 |
| **流水线（Pipeline）** | 固定阶段 Agent 串联 | 稳定、适合 ETL；灵活性差 |
| **去中心化 / 自治** | Agent 间直接协商或广播任务 | 扩展性好；难调试、易重复劳动 |
| **黑板 / 共享状态** | 各 Agent 读写公共 State | 适合复杂协同；需状态机设计 |

**去中心化调度典型实现**：

- **消息总线**：Agent 订阅 topic，自主认领任务（需幂等 + 锁）；
- **拍卖 / 竞标**：任务广播，Agent 自评能力后 bid；
- **P2P 委托**：Agent A 直接把子任务转给 B，无中心节点。

**优缺点**：

- ✅ 无单点瓶颈、可水平扩展、专长 Agent 自治演进；
- ❌ 任务重复下发、结果冲突、全局一致性差、链路难追溯。

**适用场景**：

- 去中心化：开放域研究、多专家辩论、大规模并行搜索；
- 主从：工业 CAD、企业 workflow、**需要审计和确定性**的场景（我的 Sketch 项目选主从）。

**我的选型**：主 Agent + `cad_agent` 子 Agent——CAD 任务有严格 API 白名单和文件状态，中心编排更可靠；子 Agent 内自治 50 轮 tool loop，但**不能**再 spawn（防递归）。

### Q3. 如何拆分复杂任务给子 Agent，保证不重复下发？

**拆分原则**：

1. **按能力域切**：CAD 建模 vs 文件搜索 vs 通用推理——我的 `cad_agent` 专责 NCTI；
2. **按上下文边界切**：长脚本、多模态附件只在子 Agent 编码（`attachments.py`），主 Agent 纯文本；
3. **按状态边界切**：续编状态在 `current_file` + `.py`，不在 Agent 内存重复传全文。

**防重复下发**：

| 手段 | 本项目实现 |
|------|------------|
| **结构化产物** | `write_file`/`edit_file` 捕获 `produced_file`，返回 `[产出文件] path` |
| **幂等任务描述** | `current_file` 续编时 task 写明「继续编辑该文件」 |
| **剥离 spawn 工具** | 子 Agent 工具集去掉 `cad_agent`/`agent` |
| **主 Agent Prompt** | `cad_agent` description 写 MANDATORY，但已有文件时传 `current_file` 而非重新新建 |
| **任务去重（通用）** | 任务 ID + 已完成集合；或 DAG 调度器标记节点状态 |

**面试话术**：「复杂任务按**能力 + 上下文 + 状态**三维切；防重复靠**结构化产物路径**和**spawn 剥离**，而不是指望 LLM 记得别重做。」

### Q4. 子 Agent 结果矛盾怎么设计？任务状态流转如何保证可追溯和断点续跑？

**结果矛盾场景**：子 Agent A 说「已创建 circle」，子 Agent B 说「文件不存在」；或两次 spawn 改了同一文件。

**设计思路**：

1. **单一事实源（SSOT）**：Plan B 以 `output/<session_id>/*.py` 为真相，Agent 对话只是索引；
2. **结构化元数据优先于自由文本**：`[产出文件] path` 比模型口述「我保存了」可靠；
3. **冲突仲裁层级**：文件系统 > 工具返回 > LLM 自然语言；
4. **版本 / 时间戳**：`session.json` 记录 `saved_at`；文件侧可用 git 或备份。

**状态流转与可追溯**：

```
用户消息 → messages[] → tool_calls[] → tool results → (压缩层) → 下一轮
                ↓
         .corecax/sessions/<id>.json  （save_session）
                ↓
         /resume 加载 messages + model
```

| 能力 | 实现 |
|------|------|
| **会话持久化** | `session.py`：messages + model + saved_at |
| **会话分区** | `output_dir = output/<session_id>`，并发不互相覆盖 |
| **压缩留摘要** | Layer2/3 摘要写入 messages，旧轮删除但有关键决策 |
| **断点续跑** | load_session + 主 Agent 传 `current_file` 续编 |

**生产级增强**（可答设计题）：

- 每步 tool_call 写 **Event Log**（WAL）：`{turn, tool, args, result_hash, ts}`；
- 任务状态机：`pending → running → success/failed`，支持从 last_success_event 重放；
- LangGraph / Temporal 等做**持久化 checkpoint**。

### Q5. 子 Agent 超时失败：重试、降级、兜底

**我的项目现状**：

- 子 Agent 异常 → `return f"[{self.name}] 错误：{e}"`（`skill_agent.py:198`）；
- 达 `max_rounds=50` → 返回「未完成」，主 Agent 可换策略或告知用户；
- 工具级异常 → `_exec_tool` 捕获，返回 `Error executing...` 字符串，**不抛崩整个 loop**。

**完整 Agent 架构下的分层策略**：

| 层级 | 策略 | 示例 |
|------|------|------|
| **工具级重试** | 瞬态错误重试 2–3 次（网络、限流） | HTTP 429 backoff |
| **子 Agent 重试** | 换 prompt / 缩小任务 / 换模型 | 「只改半径，别重写」 |
| **降级** | 规则引擎、模板、人工确认 | CAD 失败 → 输出伪代码草稿 |
| **兜底** | 明确失败原因 + 用户可操作项 | 「请提供半径数值」 |
| **熔断** | 同一 `current_file` 连续失败 N 次停止 spawn | 防死循环 |

**超时设计**：`ThreadPoolExecutor` 可对单 tool 设 `future.result(timeout=...)`；子 Agent 整体设 wall-clock 超时，超时返回 partial result + checkpoint。

### Q6. Agent 为什么需要记忆模块？短记忆 / 长记忆实现方式及解决的问题

**为什么需要**：LLM 上下文有限；多轮任务要保留目标、参数、中间结论；跨会话要恢复身份与进度。

| 类型 | 存什么 | 典型实现 | 解决的问题 |
|------|--------|----------|------------|
| **短记忆（工作记忆）** | 当前对话 messages、tool 结果 | `Agent.messages` | 多轮连贯、工具链上下文 |
| **压缩短记忆** | 摘要替代旧轮 | `ContextManager` 三层压缩 | token 触顶、成本、延迟 |
| **长记忆（持久）** | 跨会话事实、用户偏好 | `session.json`、向量库、文件 | 断点续聊、知识积累 |
| **外部状态记忆** | 任务产物 | `output/*.py`、`current_file` | 大对象不进 context |

**本项目映射**：

- **短记忆**：`messages` + system prompt（Skill SOP、API Index）；
- **压缩**：50% snip tool 输出 → 70% LLM 摘要 → 90% hard collapse（`context.py`）；
- **长记忆**：`save_session` / `load_session`；
- **文件即长记忆**：CAD 脚本实体存在磁盘，对话只记路径——这是 Plan B 核心。

**CAD-Agent-Education 补充**：4 段式摘要（目标/进度/参数/待办），比纯截断更能保留续编关键参数。

### Q7. Agent 无法解析工具返回的 JSON，怎么优化？

**根因**：模型输出非 JSON、字段缺失、类型错、多余 markdown 包裹、中文标点。

**优化手段**（FindJobs + 通用）：

1. **Structured Output / JSON Schema**：API 层 `response_format` 或 LangChain `with_structured_output`；
2. **Prompt 约束**：「只输出 JSON，不要 ```」+ Few-shot 正例；
3. **解析容错链**：`json.loads` → 正则提取 `{...}` → `json5` / `repair_json`；
4. **字段级校验 + 重试**：Pydantic 校验失败，把错误喂回模型「缺字段 score」；
5. **降低 temperature**（FindJobs 评分用 0.2）；
6. **工具返回也结构化**：工具统一返回 `{"ok": true, "data": ...}`，减少模型二次编造。

**CAD 场景**：工具返回是字符串而非 JSON；主路径是 **tool name + arguments JSON** 解析失败——在 schema 里约束参数类型， `TypeError` 时返回明确错误让模型改参。

### Q8. 文档切片：固定长度 vs 语义切片

| 方案 | 做法 | 优势 | 劣势 |
|------|------|------|------|
| **固定长度** | 按字符/token 滑动窗口，可重叠 | 实现简单、长度可控、适合 embedding 批处理 | 语义截断、标题与正文分离、表格/code 易碎 |
| **语义切片** | 按段落/标题/句子边界，或 embedding 相似度突变点切 | 块内语义完整、检索质量高 | 块大小不均、实现复杂、边界难定 |
| **结构感知** | Markdown 标题、代码块、CAD API 章节（如 `<api_index>`） | 领域友好 | 依赖文档格式 |

**工程建议**：先结构切（标题/段落）→ 超长块再固定长度二次切；代码/API 文档**按条目**切而非按字数。

**与我的项目**：`SKILL.md` + `references/case-*.md` 是**按需 read_file**（渐进披露），等价于「索引 + 语义块加载」，避免一次性塞满 system prompt。

### Q9. RAG 上下文过长 → token 超时、回答冗余，怎么解决？

**问题链**：检索过多 chunk → prompt 膨胀 → 超时 / 成本高 → 模型重复罗列检索内容。

**解法矩阵**：

| 方向 | 手段 |
|------|------|
| **检索侧** | 减小 top_k；MMR 去冗余；重排序只留 3–5 条；查询改写 |
| **压缩侧** | 对 chunk 做 LLM 摘要再注入；只注入与 query 相关的句子 |
| **上下文工程** | 分层：摘要层 + 细节层按需 `read_file`（我做的 reference 目录） |
| **生成侧** | Prompt 要求「引用即可，勿复述全文」；结构化输出限制长度 |
| **架构侧** | 子 Agent 隔离检索上下文，主 Agent 只收结论 |
| **Agent 循环** | 同 ContextManager：snip / summarize / collapse |

**本项目非典型 RAG**，但 **三层压缩** 和 **子 Agent 隔离** 解决的是同一类「上下文过长」问题。

### Q10. 知识库频繁更新：向量库增量更新方案

（通用设计题，可结合 CAD 平台「数万零件入库」场景）

**目标**：新文档入库快、旧向量可删可改、检索一致、重建成本低。

**推荐方案**：

```
文档变更 → 变更检测（hash/版本号）
         → 切片 + doc_id + chunk_id 元数据
         → 仅对新增/修改 chunk 调 embedding API
         → upsert 向量库（同 id 覆盖）
         → 删除文档时按 doc_id 批量 delete
```

| 组件 | 设计要点 |
|------|----------|
| **ID 策略** | `doc_id + chunk_index` 稳定主键，支持 upsert |
| **变更检测** | 文件 SHA256（我在 Geo-Data-Management 用 SHA256 去重） |
| **双写期** | 新版本索引完成后切换 alias，避免检索空洞 |
| **全量重建** | 定期离线重建 + 校验 recall，作兜底 |
| **元数据过滤** | 行业/特征类型先滤 SQL，再向量检索（减小库规模） |

**CAD 平台类比**：零件 STEP 用 SHA256 去重；标注 JSON 更新走 API 回写，不必重算全库——**结构化元数据 + 按需重训/重推理** 比纯向量库更贴合该业务。

### Q11. 大模型幻觉在 Agent 工具调用场景的典型表现及优化

**典型表现**：

| 类型 | 例子（我的 CAD 场景） |
|------|----------------------|
| **捏造工具名** | 调用不存在的 `skt.AddTriangle()` |
| **捏造参数** | 无参 `skt.AddLine()`（GUI-only） |
| **错误工具选择** | 应用 `bash` 执行建模而非 `cad_agent` |
| **编造工具结果** | 声称已保存文件但实际未 `write_file` |
| **过度调用** | 重复 spawn 子 Agent |

**优化方案**（对应我的实现）：

1. **工具白名单**：`skill.allowed_tools` 只暴露 read/write/edit；
2. **API Index 正向列举**：`<api_index>` 列出全部合法接口，禁止猜测；
3. **动态工具过滤**：未激活技能的工具对模型不可见（CAD-Agent-Education）；
4. **结构化产物校验**：从 tool args 捕获 `produced_file`，不依赖模型口述；
5. **执行后验证**：脚本语法检查、NCTI 运行时试跑（可扩展）；
6. **Prompt 纪律**：缺参数必须追问，禁止默认假设（`CAD_SYSTEM_PROMPT` Parameter validation）；
7. **降低开放度**：子 Agent 任务域收窄，主 Agent 只做编排。

### Q12. Agent 调用工具完整执行流程（从用户提问到总结）

结合 **Sketch-Modeling-Agent** 主 Agent 调 `cad_agent` 的完整链路：

```
① 用户输入
   「在草图里画一个半径 50 的圆」(+ 可选附件路径)

② 主 Agent 组装上下文
   system_prompt(可用工具列表) + messages 历史
   → ContextManager.maybe_compress() 按需压缩

③ 第一次 LLM 调用
   messages + tools schema → 模型返回 tool_calls: cad_agent

④ 主 Agent 执行工具 cad_agent
   SkillAgentTool.execute():
     [A] load cad-sketch SKILL.md
     [B] 生成 references 目录（case-init, case-constraint...）
     [C] 拼接 CAD_SYSTEM_PROMPT + skill SOP + api_index
     [D] _prepare_task(task, current_file?) 续编改写
     [E] 工具集过滤 → read_file, write_file, edit_file
     [F] spawn 子 Agent

⑤ 子 Agent 内部循环（最多 50 轮）
   LLM → 可能 tool_calls: read_file(case-init.md)
        → tool result 回灌 messages
        → LLM → write_file(output/xxx/session_xxx/circle.py)
        → 压缩层按需 snip/summarize
        → LLM 文本回复（一句话 + 遵守 output_discipline）

⑥ 子 Agent 返回主 Agent
   「Created output/.../circle.py with c1 radius 50.」
   + [产出文件] output/.../circle.py

⑦ 主 Agent 第二次 LLM 调用
   将 tool result 写入 messages → 模型生成面向用户的自然语言总结

⑧ 用户看到结果
   CLI 已流式打印子 Agent 工具进度；主 Agent 补充说明或确认下一步
```

**关键数据结构**：

```text
messages = [
  {role: user, content: ...},
  {role: assistant, tool_calls: [{name, arguments, id}]},
  {role: tool, tool_call_id, content: "工具返回字符串"},
  {role: assistant, content: "最终回复"},
]
```

## 五、高频追问速查表

| 问题 | 一句话答案 |
|------|------------|
| 为什么不用 LangGraph？ | 草图 Agent 要轻量循环 + Skill 流水线；LangGraph 适合复杂图状态，早期验证后迁移 CoreCAX |
| 为什么不用 MCP？ | 闭源 NCTI 需自定义白名单与文件状态；Skill 机制类似按需能力发现，后续可包 MCP adapter |
| 子 Agent 能嵌套吗？ | 不能，spawn 工具已从子 Agent 剥离 |
| 三层压缩丢信息怎么办？ | 摘要保留路径/参数/待办；CAD 真相在 .py 文件 |
| DANN 解决什么？ | SolidWorks/CATIA STEP 分布漂移 |
| 混合推理为什么取交集？ | AAG+几何取交集降误检，漏检用纯 AI 或几何补 |
