## Q3. 为什么选择向量 + 关键词双路检索？检索结果怎么做重排序？

**【面经 · 标准答法】**

### 为什么双路

| 单路盲区 | 双路互补 |
|----------|----------|
| 纯向量 | 「学号规则」「具体课程名」等精确词匹配弱 |
| 纯 BM25 | 同义词、口语化问法召回差 |

**典型融合：**

1. 向量 TopK（如 20）+ BM25 TopK（如 20）
2. **RRF** 融合：`score = Σ 1/(k+rank)`，k 常取 60
3. **Cross-Encoder Rerank**：对融合 Top50 精排 → 取 Top3~5 进 prompt

### Rerank 解决什么

> 双路提高 **Recall**；Rerank 提高 **Precision**，避免无关 chunk 污染 context。

**【项目 · 诚实 + 类比】**

> 我主项目 **没有用向量+BM25 标准 RAG**。类比能力：
> - **API Index** ≈ 高精度关键词白名单  
> - **reference 按需 read** ≈ retrieve-on-demand  
> - **CAD 混合推理（几何 / GNN / 交集）** ≈ 多路召回 + 融合  

**若我做校园 RAG：** 校规 PDF + FAQ；课号类 query 提高 BM25 权重；Rerank 用 bge-reranker 或 Cohere。

## Q4. 教务登录授权的核心难点是什么？你怎么解决的？

**【面经 · 标准答法】**

### 核心难点

| 难点 | 说明 |
|------|------|
| **无 OAuth 开放接口** | 教务系统常只有网页登录，无标准 API |
| **验证码 / 滑块** | 自动化登录难，需人工或打码（合规风险） |
| **Session 绑定** | Cookie + CSRF + 短 TTL，和多用户 Agent 服务冲突 |
| **安全合规** | 不能把用户明文密码落库；Session 要加密隔离 |
| **多租户** | 每用户独立 Session，不能串号 |

### 常见解法

1. **OAuth 代理不可用时的「用户自带 Session」** — 浏览器插件/手动粘贴 Cookie（体验差）
2. **服务端模拟登录** — 加密存凭证，定时刷新（维护成本高）
3. **官方开放平台** — 若有统一身份认证（CAS），走 ticket 换 token
4. **Session 托管** — Redis 存 `{user_id: encrypted_cookie, expire_at}`，Agent Tool 带 Cookie 调教务

**【诚实】**

> 我 **没有做过教务登录**。Sketch/FindJobs 是 **内网/本地 API**，无第三方 Cookie 授权。  
> 若做会：**密码不落库、Session 加密存 Redis、按 user_id 隔离、过期强制重新授权、审计每次代调教务 API**。

## Q5. 获取 Session 后，怎么保证有效性和续期？

**【面经 · 标准答法】**

```
Session 存储结构（Redis）：
  key: session:{user_id}
  value: { cookie, csrf_token, created_at, expire_at, last_used_at }
  TTL: 略小于教务实际过期时间
```

**保活策略：**

| 手段 | 说明 |
|------|------|
| **主动探测** | 定时/请求前用轻量接口（如个人信息）探活 |
| **滑动续期** | 每次成功调用后 `EXPIRE` 延长 Redis TTL |
| **被动失效** | 教务返回 401/跳转登录 → 标记 invalid，通知用户重登 |
| **续期接口** | 若有 refresh 或 keep-alive URL，后台定时任务刷新 |
| **熔断联动** | 连续失效 → 熔断教务 Tool，避免打爆无效请求 |

**【项目 · 类比】**

> Sketch 的 `session.json` + 断点续聊是 **会话持久化**，但不是 Cookie 续期。思路类似：**状态外置 + 失效可恢复 + 过期明确提示**。

## Q6. LangChain Agent ReAct 架构的执行链路具体是什么样的？

**【通用 + 项目】**

### ReAct 链路（LangChain 视角）

```
User Input
  → AgentExecutor
       → LLM（bind Tools）
       → 输出：文本 或 tool_calls
       → 若有 tool_calls：
            → 执行 Tool → Observation（字符串/JSON）
            → 追加到 chat_history
            → 再调 LLM（循环）
       → 若无 tool_calls：Final Answer
  → 返回用户
```

**LangChain 组件映射：**

| 组件 | 作用 |
|------|------|
| `ChatModel` | 推理 |
| `tools[]` | 可调用能力 |
| `AgentExecutor` | 循环 + max_iterations |
| `MessagesPlaceholder` | 历史消息 |

**【项目】**

1. **CAD-Agent-Education**：LangGraph 显式图，节点仍是 **LLM → Tool → LLM**
2. **Sketch `agent.py`**：手写 `while tool_calls`，等价 ReAct，还加了 **并行 Tool**（`ThreadPoolExecutor`）

**与教科书差异：**

> 不强制输出 `Thought:` 行，用 **native tool calling**；Observation 结构化后再回灌。

## Q7. 多轮对话怎么实现？如何保持上下文记忆？

**【面经 + 项目】**

### 多轮实现

1. **服务端存 `messages[]`** — 每轮 append user/assistant/tool
2. **session_id** 关联用户与历史
3. **请求时带上最近 N 轮** 或 **摘要 + 最近 N 轮**

### 记忆分层（校园 Agent 常见）

| 层 | 内容 |
|----|------|
| 短期 | 最近 K 轮原文 |
| 中期 | 滑动窗口外的 LLM 摘要 |
| 长期 | 用户偏好 / 课表缓存（结构化 DB，非全塞 prompt） |

**【项目】Sketch：**

- `session.json` 持久化消息
- **三层 Memory 压缩**（50% / 70% / 90% 窗口触发）
- **文件即状态** — 脚本在磁盘，不靠模型记代码
- 子 Agent 长输出 **不回流** 主 Agent 全文，只留摘要

**【项目】CAD-Agent-Education：**

- 4 段式摘要：目标 / 进度 / 参数 / 待办

## Q8. 滑动窗口 + 历史摘要压缩的具体逻辑？为什么保留最近 3 轮？

**【面经 · 标准答法】**

### 典型逻辑

```
messages = [system, ...history..., user_new]

if total_chars > THRESHOLD:
    old = messages[1:-WINDOW]   # 窗口外旧对话
    summary = LLM.summarize(old) # 结构化摘要
    messages = [system, summary_msg, ...last WINDOW rounds..., user_new]
```

**为什么保留最近 3 轮（面经常见取舍）：**

| 原因 | 说明 |
|------|------|
| **指代消解** | 「那门课」「改成周二」依赖上一轮 |
| **Tool 链连贯** | 上一步 Tool 结果仍可能被引用 |
| **成本** | 3 轮通常 2k~4k token，可控 |
| **经验值** | 校园问答多 1~3 轮澄清，再早的可压摘要 |

> 3 不是定理，应 **按 token 预算和评测调**；有的用 5 轮或「最近 4000 token」。

**【项目】**

> 我用 **token 比例阈值** 而非固定 3 轮：Layer1 snip → Layer2 摘要 → Layer3 硬折叠。  
> **保留最近 N 轮** 的思想一致，但 N 是 **动态** 的，且摘要 Prompt 要求保留 **路径、参数、错误、待办**（CAD 场景）。

## Q9. 为什么摘要触发阈值设为 8000 字符？这个值怎么确定？

**【面经 · 标准答法】**

8000 **字符** ≈ 中文 **2500~4000 token**（粗算 1 汉字 1~2 token），常见推导：

| 因素 | 考虑 |
|------|------|
| 模型窗口 | 如 32k token，要留 **检索 chunk + 生成 + system** |
| 安全边际 | 历史占 **30%~40%** 窗口，其余给 RAG 和回答 |
| 触发频率 | 太低频繁摘要（慢+丢细节），太高易触顶 |
| 实测 | 用线上/测试集 **扫 7k/8k/10k**，看答案质量与延迟 |

**确定方法（面试加分）：**

1. 统计对话 **P95 字符长度**
2. 在验证集 A/B：**摘要质量**（关键槽位保留率）vs **LLM 成本**
3. 8000 多为 **「工程经验起点」**，不是最优解

**【项目】**

> `context.py` 用 **窗口百分比**（50/70/90%）而非 8000 字符，因为 CAD 对话 **tool 返回和代码块** 波动大，固定字符不如 **相对阈值** 稳。  
> `_approx_tokens = len(text) // 3` 粗算触发。

## Q10. 三态熔断器设计思路是什么？解决了什么问题？

**【面经 · 标准答法】**

### 三态（典型 FSM）

```
CLOSED（正常）
  → 失败率/连续失败超阈值
OPEN（熔断，快速失败）
  → 等待 cooldown
HALF_OPEN（试探）
  → 放行少量请求
       → 成功 → CLOSED
       → 失败 → OPEN
```

### 解决的问题

| 问题 | 熔断作用 |
|------|----------|
| 教务 API 挂了 | 避免 Agent 无限重试 Tool，拖垮线程、烧 token |
| LLM 超时雪崩 | 快速失败 + 降级文案（「教务系统繁忙，请稍后再试」） |
| 级联故障 | 保护 Redis、DB、下游 |

### Agent 场景参数

- **按依赖分桶**：`breaker:jwxt_api`、`breaker:llm`
- **半开探测**：每 30s 放 1 个请求
- **降级策略**：RAG-only 答通用规章，禁成绩查询 Tool

**【诚实 + 类比】**

> 我 **没有实现三态熔断器**。Sketch 有 **max_rounds 上限**、Tool 失败回灌、单 attachment skip — 是 **局部失败隔离**，不是服务级熔断。  
> CAD 平台 **5 态入库状态机** 是业务状态，不是 Hystrix 式熔断，但 **「失败 → 停写 → 人工/重试」** 思路相通。

## Q11. Redis 信号量限流怎么实现？并发达到上限怎么处理？

**【面经 · 标准答法】**

### Redis 信号量（分布式并发控制）

**目标：** 全集群同时最多 N 个请求在跑（保护 LLM QPS / 教务接口）。

**实现方式 1：计数器 + TTL**

```text
KEY: semaphore:agent:{resource}
INCR 成功且 value <= N → 获得许可
DECR 或 DEL → 释放
```

**实现方式 2：Redisson `RSemaphore`**

```java
RSemaphore sem = redisson.getSemaphore("agent:llm");
sem.tryAcquire(3, TimeUnit.SECONDS);  // 等待或超时
try { ... } finally { sem.release(); }
```

**实现方式 3：Lua 保证原子性**

> INCR/DECR + 判断上限在一个 Lua 脚本里，防并发竞态。

### 达到上限时

| 策略 | 适用 |
|------|------|
| **快速失败** | 返回 429 +「系统繁忙」 |
| **排队等待** | `tryAcquire(timeout)`，超时再失败 |
| **优先级队列** | VIP / 重试请求不同队列 |
| **降级** | 只返回缓存 FAQ，不调 LLM |

**【诚实】**

> 我项目 **未用 Redis 信号量**。FindJobs 是低并发 Flask；Sketch 是 CLI 单用户。  
> 若 Agent 上生产，我会对 **LLM 调用** 和 **教务 Tool** 分别设信号量，并配 **排队超时 + 429**，避免线程池打满。

## Q12. 项目为什么选用 PostgreSQL 而不是专门的向量数据库？

**【面经 · 标准答法】**

| 选 PostgreSQL（+ pgvector） | 选 Milvus/Qdrant 等 |
|----------------------------|---------------------|
| 业务数据已在 PG，**事务一致** | 亿级向量、极致 ANN 性能 |
| 量级百万级内向量 **够用** | 复杂混合检索、多副本集群 |
| **运维一套栈**，团队熟悉 SQL | 专职向量团队维护 |
| 权限/Join/审计与业务表 **同库** | 需同步业务 metadata |
| 校园 FAQ 量级通常不大 | 超大规模或多模态专库 |

**典型架构：**

> `documents` 表 + `embedding vector(1536)` + HNSW/IVFFlat 索引；BM25 仍可用 Elasticsearch 或 PG 全文检索。

**面试话术：**

> 不是「向量库不好」，是 **规模与团队边界** 下的取舍；量上来后再 **拆专用向量库** 或 **PG + 外挂 ES** 很常见。

**【项目 · 诚实】**

> 我没有 PG+pgvector 落地。Sketch 用 **文件 + Git** 管知识；FindJobs 用 **Python dict 课程库**。  
> 若 FindJobs 岗位/JD 上万条，我会考虑 **PG 存结构化 + pgvector 做语义匹配**，与业务表 Join 方便。

## Q1. 介绍一下 12306 高并发抢票项目的整体设计

**【面经 · 标准答法】**

```
                    ┌──────────────┐
  用户 → CDN/网关 → │  限流/令牌    │
                    └──────┬───────┘
                           ▼
              ┌────────────────────────┐
              │  抢票服务（无状态，可水平扩） │
              └────────────┬───────────────┘
         ┌─────────────────┼─────────────────┐
         ▼                 ▼                 ▼
    Redis（余票/锁/令牌）   MySQL（权威数据）   MQ（异步下单）
         ▲                 ▲
         └──── Canal binlog 同步 ────┘
```

**核心原则：**

1. **读多写少** — 查询走缓存，扣票走 Redis 预减 + 异步落库  
2. **流量削峰** — 令牌/验证码/队列，把瞬时 QPS 压住  
3. **数据最终一致** — Redis 与 MySQL 通过 Canal + 补偿  
4. **热点隔离** — 热门车次独立缓存 key、独立锁  

**【诚实】**

> 这是我学习的 **经典架构题**，本人 **未参与 12306 类项目**。我有 **CAD 平台 5 态状态机、入库 API** 经验，理解 **状态流转与一致性**，但不是抢票量级。

## Q2. 用户注册模块做了哪些高并发优化？

**【面经 · 标准答法】**

| 优化 | 作用 |
|------|------|
| **布隆过滤器** | 快速判断用户名 **可能存在**，避免无效查库 |
| **Redis 预查** | 热点用户名缓存 |
| **分库分表** | 用户表按 id 哈希水平拆 |
| **异步写** | 注册成功消息 MQ 异步发邮件/积分 |
| **接口限流** | IP + 设备维度防刷 |
| **唯一索引** | DB 层兜底重复注册 |

**【诚实】** 未做过注册高并发模块。

---

## Q3. 为什么要用布隆过滤器？它解决了什么问题？

**【面经 · 标准答法】**

**问题：** 注册时「查用户名是否存在」若每次都打 MySQL，高并发下 DB 成为瓶颈。

**布隆过滤器：**

- 位数组 + 多个 hash 函数
- **判断不存在 → 一定不存在**（可跳过 DB）
- **判断存在 → 可能存在的误判**（需再查 DB/Redis 确认）

**效果：** 大量「随机撞名」请求被 **挡在 DB 外**，降低读压力。

**代价：** 有误判率、**不能删元素**（见 Q4）。

---

## Q4. 布隆过滤器无法删除，用户注销后怎么处理？

**【面经 · 标准答法】**

| 方案 | 做法 |
|------|------|
| **计数布隆过滤器（CBF）** | 支持 delete（实现复杂） |
| **双 BF 轮换** | 定期新建 BF，旧 BF 过期淘汰 |
| **黑名单补偿** | 注销用户名加入 **Redis Set**（可删），查询时 **先查黑名单** 再查 BF |
| **接受误判** | 注销后 BF 仍「可能存在」，**最终以 DB 为准**（注销态在 DB 标记） |

**面经常见组合：** BF 挡无效流量 + **Redis Set 存已注销名** + DB 权威。

---

## Q5. 为什么用 Redis Set 存注销用户名？Set 大了会有什么问题？

**【面经 · 标准答法】**

**为什么 Set：**

- O(1) `SISMEMBER` 判断是否在注销名单  
- 支持 **删除/新增**，弥补 BF 不能删  
- 语义清晰：`cancelled_usernames`

**Set 过大问题：**

| 问题 | 影响 |
|------|------|
| **内存** | 全量用户名占 Redis 内存 |
| **持久化** | RDB/AOF 变大，恢复慢 |
| **单 key 过大** | 集群 slot 热点、阻塞风险 |

**优化：**

- 只存 **近期注销** + TTL  
- 分片 Set：`cancelled:{hash%256}`  
- 超大后 **Bloom + DB 注销标记** 为主，Set 只作热数据

## Q6. 令牌机制具体逻辑？令牌和展示余票为什么要解耦？

**【面经 · 标准答法】**

### 令牌机逻辑

```
放票前：用户排队/答题 → 发放有限 token（JWT 或 Redis 计数）
持 token 才能进入「真正扣票接口」
无 token → 直接拒绝（挡掉大部分流量）
```

**目的：** **削峰** — 把 100 万 QPS 变成 1 万有效抢票 QPS。

### 为什么与「展示余票」解耦

| 解耦点 | 原因 |
|--------|------|
| **余票展示** | 可缓存、可延迟、允许短暂不准（「有票/无票」粗粒度） |
| **扣票 token** | 必须精确、防超卖、与库存强一致 |
| **独立扩容** | 查询 CDN 缓存 vs 写路径 Redis 锁，负载模型不同 |
| **防刷** | 爬虫刷余票接口不应影响扣票链路 |

> 展示用 **只读缓存**；扣票用 **token + 分布式锁 + Redis 预减**。

## Q7. 分布式锁在抢票中具体用在哪里？锁粒度是列车级还是座位级别？

**【面经 · 标准答法】**

**使用位置：** **扣减库存 / 占座** 临界区，保证同一座位不会被两人同时买到。

**粒度取舍：**

| 粒度 | 优点 | 缺点 |
|------|------|------|
| **列车级** | 锁少、实现简单 | 并发度极差，一列车串行 |
| **区间/车厢级** | 中等并发 | 仍可能热点 |
| **座位级** | 并发最高 | 锁数量大，需 Redis 集群 |

**实践：** 常用 **「车次+日期+席别」段锁** 或 **Redis 预减库存 + Lua 原子 decr**，锁粒度到 **库存 bucket** 而非物理每个座位，平衡并发与复杂度。

**实现：** Redisson `RLock`、`SET key NX EX` + Lua 释放。

---

## Q8. 分布式锁获取失败，请求直接返回还是重试？

**【面经 · 标准答法】**

| 场景 | 策略 |
|------|------|
| **抢票扣库存** | **快速失败** 或 **极短重试 1~2 次**（10~50ms），避免线程堆积 |
| **异步补偿任务** | 可退避重试 |
| **用户侧** | 返回「票已抢完/请重试」，前端随机 jitter 再试 |

**原则：** 高并发写路径 **不重试风暴**；`tryLock(waitTime)` 设上限，失败即释放连接。

## Q9. Redis 余票和 MySQL 数据不一致怎么解决？

**【面经 · 标准答法】**

**架构：**

1. **MySQL 为权威源**（最终一致）  
2. **Redis 为抢票缓存**（预减库存，高性能）  
3. **Canal 监听 binlog** → 同步 Redis  
4. **下单成功** → MQ 异步写 MySQL 订单  
5. **定时对账** — Redis vs MySQL 库存 diff 告警  
6. **补偿任务** — 以 DB 为准修复 Redis  

**超卖防护：**

- Redis **Lua 原子 decr**，减到 0 拒绝  
- MySQL **乐观锁** `update ... where version=? and stock>0`  
- 失败订单 **回滚 Redis** 或异步补票

---

## Q10. Canal 同步 Redis 失败怎么办？有没有重试机制？

**【面经 · 标准答法】**

| 机制 | 说明 |
|------|------|
| **Canal 客户端重试** | 消费失败 N 次后进入死信/人工 |
| **本地消息表** | 同步任务落库，定时扫 **pending** 重推 Redis |
| **幂等** | 按 binlog offset / 业务 id 幂等 SET |
| **对账修复** | 每小时全量/抽样比对库存 |
| **监控告警** | lag、失败率、Redis key 缺失 |

**面试金句：**

> 同步链路 **至少一次投递 + 幂等消费 + 对账兜底**，不能单靠「不重试」。

**【诚实】** 未做过 Canal 链路，理解来自架构学习。
