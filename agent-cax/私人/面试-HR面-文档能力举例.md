# HR 面 · 文档能力三举例（SKILL.md / 方案拆分 / 测试 Case）

> 适用场景：HR 问「有没有写过文档？」「怎么从需求到落地？」「怎么保证质量？」  
> 每个例子控制在 **40～60 秒**；三例串联版约 **90 秒**，见文末。

---

## 一、SKILL.md —— 把「能力说明 + 作业规范」写成可配置文档

### HR 可以怎么理解

一份给 AI Agent 用的 **「岗位作业手册」**：不是 Word 需求书，而是 **需求边界 + 工具权限 + 标准流程** 写进 Markdown，系统启动时自动加载。

### 项目里真实写了什么

路径：`国创工软\Sketch-Modeling-Agent\skills\cad\cad-sketch\SKILL.md`

**1. 元信息（YAML frontmatter）—— 能力注册表**

```yaml
name: cad-sketch
description: 用户要做草图建模（画线、圆、约束…）时触发
allowed-tools:
  - write_file
  - read_file
  - edit_file
```

- **什么时候用这个能力**（Trigger）
- **允许用哪些工具**（白名单，防止乱调 bash、乱 spawn 子 Agent）

**2. 正文 —— 设计说明 + 操作 SOP**

| 章节 | 内容 |
|------|------|
| Overview | 初始化、11 种几何、12 种约束、5 种约束编辑 |
| Prerequisites | 画之前判断草图状态（不存在 / 未打开 / 已打开） |
| Workflow | 单步、多步、改约束三种流程 |
| Cross-step Variable Rules | 圆角、约束须引用前面变量名，避免续编丢代码 |

**3. 配套 reference（如 `references/case-init.md`）—— API 手册附录**

子 Agent 按需 `read_file` 加载，不在 spawn 时一次性塞满上下文（渐进披露）。

### 面试话术（40～60 秒）

> 实习里 CAD 建模能力我没有写死在代码里，而是写成 **SKILL.md**：上面写 **什么时候触发、能用哪些工具**，下面写 **标准作业流程和注意事项**。新增一种建模场景，主要是 **加文档、改配置**，主程序不用动。  
> 这和贵司 JD 里说的 **需求文档、设计文档、可追溯** 是一回事——只是把文档对象从「给人看」扩展成 **给 Agent 执行**，保证行为可配置、可版本管理、可复用。

### 可能的 HR 追问

**「和普通技术文档有什么区别？」**

> 普通文档给人读；SKILL 还要被程序解析——有 frontmatter 字段、工具白名单，改一行就可能影响 Agent 行为，所以更强调 **结构化和边界清晰**。

## 二、方案拆分 —— 从业务痛点拆成可落地模块

HR 要听：**怎么从模糊需求拆成几个能交付的东西**，不是堆架构名词。

### 例子 1：Sketch-Modeling-Agent（主答，推荐）

**原始需求（业务语言）**  
用户用自然语言做 CAD 草图，还要多轮改，不能越改越乱。

**拆出的 4 个核心问题 → 4 个方案**

| 痛点 | 方案 | 一句话 |
|------|------|--------|
| 脚本太长撑爆对话 | 主 Agent + `cad_agent` 子 Agent | 长脚本只在子 Agent 里，主对话只留一行结论 |
| 闭源 API 容易被编造 | SKILL 白名单 + `<api_index>` | 模型只能看到合法接口 |
| 续编容易整文件重写丢几何 | Plan B：`current_file` + `edit_file` | 状态在 `.py` 文件，续编先读后改 |
| 多轮 token 爆炸 | 三层压缩 50% / 70% / 90% | 工具输出裁剪 → LLM 摘要 → 硬折叠 |

**六阶段流水线（HR 简化版）**

> 加载技能 → 选参考案例 → 拼系统提示 → 准备任务 → 过滤工具 → 启动子 Agent

新增能力只动前两步配置，主循环零改动。

**面试话术**

> 我没有一上来写代码，而是先把 **「谁负责编排、谁负责生成脚本、状态放哪、上下文怎么控」** 四件事拆开。拆完每块都有明确交付物：子 Agent 模块、SKILL 文档、文件续编协议、压缩策略。这和 JD 里 **「理解需求 → 技术路径 → 模块选型 → 原型验证」** 是对齐的。

---

### 例子 2：FindJobs-Agent（备用，30 秒）

**原始需求**：学校要看培养方案是否支撑学生去目标岗位。

**拆分**：

1. 学生侧：简历 → **15 项技能评分**（结构化 JSON）
2. 画像侧：四维能力雷达 + **TOP5 岗位**
3. 学校侧：**课程-岗位覆盖度**算法
4. 展示侧：React 三栏同屏

对应 JD 的 **「知识应用 + 决策分析」**，场景是就业而非政务。

---

### 例子 3：CAD 几何特征识别平台（可选，体现全链路）

**原始需求**：STEP 零件要训 GNN 识别圆角/倒角。

**拆分**：数据入库 → 3D 标注 → STEP 转图 → 训练 → 推理部署，5 个子系统；中间用 **seg/inst/bottom JSON** 贯穿，避免多工具手工对账。

说明不只会 Agent，也有 **从数据到模型的方案拆分** 经验。

## 三、测试 Case —— 用用例把设计「验住、写清楚」

HR 不需要懂 pytest；要说的是：**关键设计有没有被测试锁住、出问题能不能定位**。

### 向 HR 解释「测试是什么」

> 每个测试 case 对应一条 **设计承诺**。比如「子 Agent 不能再 spawn 子 Agent」，测试就断言 spawn 类工具被剥离；「续编靠 current_file」，测试就断言传入路径后任务描述会被改写成「先 read 再 edit」。

源码路径：`国创工软\Sketch-Modeling-Agent\tests\`

---

### 类型 A：配置 / 文档解析（对应 SKILL.md 可靠性）

文件：`test_cad_agent.py`

| Case | 验证什么 |
|------|----------|
| `test_parse_valid_skill_file` | 正常 SKILL.md 能解析 name、description、allowed-tools |
| `test_parse_skill_file_no_frontmatter` | 缺 frontmatter 必须报错，不能静默失败 |
| `test_parse_skill_file_zero_indent_list` | YAML 列表格式不同也能解析，避免子 Agent **零工具** |

**话术**：「SKILL 是 Agent 的配置源，解析错了整个系统会 silently break，所以写了 **边界 case**：缺字段、格式异常、工具列表为空都要有明确行为。」

---

### 类型 B：架构约束（对应方案拆分是否落地）

文件：`test_skill_agent.py`

| Case | 验证什么 |
|------|----------|
| `test_agent_spawn_tools_constant` | 子 Agent 工具集必须去掉 `agent` / `cad_agent` |
| `test_skill_mode_uses_whitelist` | 有 Skill 时只保留白名单工具 |
| `test_prepare_task_hook_is_called` | 续编逻辑（`_prepare_task`）一定会被执行 |
| `test_file_path_appended_when_produced` | 产出文件路径结构化回传，主 Agent 能续编 |
| `test_result_returned_untruncated` | 子 Agent 结果不能截断，否则主 Agent 反复 spawn |

**话术**：「方案拆分不是 PPT，我用测试把 **架构决策写死**：防递归、白名单、续编路径回传，改代码跑测试就知道有没有破坏设计。」

---

### 类型 C：安全与工程兜底（体现责任心）

文件：`test_tools.py`

| Case | 验证什么 |
|------|----------|
| `test_bash_blocks_rm_rf` | 禁止危险 shell 命令 |
| `test_bash_timeout` | 工具执行有超时 |
| `test_all_tools_have_valid_schema` | 每个工具 JSON Schema 合法，模型能正确调参 |

**话术**：「Agent 会调工具，schema 错了模型就调不对；危险命令要拦。类似 JD 里的 **测试报告、可追溯**——关键路径有 case 覆盖。」

---

### HR 追问：「有没有写给人看的测试报告？」

**诚实 + 补救**

> 正式 Word 版测试报告还在积累，但项目里 **pytest + 用例命名即说明**（如 `test_skill_mode_uses_whitelist`），每个 case 对应一条设计约束。入职后可以按贵司模板整理成 **测试报告 + 评估说明**；FindJobs 那边我也用固定简历样本做过 **15 项 JSON 输出稳定性** 的手工验证。

## 四、三例串联（HR 问「文档能力具体举例」· 约 90 秒）

> 我实习的 CAD Agent 项目里，文档能力主要体现在三层。  
> **第一层**，把建模能力写成 **SKILL.md**：什么时候触发、能用哪些工具、标准流程是什么，相当于 **需求 + 设计 + 操作手册** 合一，还能热插拔扩展。  
> **第二层**，接到「自然语言建模、多轮续编」这种模糊需求后，我拆成 **主子 Agent、文件即状态、工具白名单、上下文压缩** 四块，每块有明确职责，对应贵司说的技术路径和模块选型。  
> **第三层**，用 **pytest 测试 case** 把设计锁住——Skill 解析、工具白名单、续编路径回传、禁止子 Agent 嵌套，都有对应用例，改坏了测试会红。  
> 所以我不是只写代码，习惯 **先写清楚边界和流程，再用 case 验证**，这和 JD 里文档体系、原型评估是一致的。
