## 业务咨询：草图识别微调可行性（领导需求）
- 领导想微调模型让"草图识别更准→LLM 脚本更准"。判断：**方向部分可行、部分被误读**。
- 识别(视觉感知)微调收益大；但脚本准不准还卡在"API 翻译 + 几何合法性"，这两块靠"结构化转译 + 求解验证"更划算；几何合法性由 NCTI 求解器决定，模型保证不了。
- 风险：微调前提是有标注数据(NCTI 私有无现成)；API 知识放 Skill/RAG 比烤进权重更灵活(内核升级权重即过期)。
- 建议路径：先 P0 结构化转译 + P1 验证闭环 + P2 澄清/知识沉淀，P3 仅当识别仍瓶颈才微调 VLM(且只调识别段)。

## 调研产出：结构化转译 + 验证闭环 设计文档
- 交付：`docs/sketch-transpile-verify-design.md`（开源项目/论文调研 + 本项目落地设计）。
- 关键参考项目：
  - **CADSmith**(arXiv:2603.26512, 2026)：多智能体生成 CadQuery，**不用微调用 RAG**；双嵌套循环=内循环排执行错误+外循环程序化几何验证(OpenCASCADE 取 bounding box/volume/**solid validity** + 独立 VLM Judge)；CD 28.37→0.74。
  - **Draw2Think**(arXiv:2605.20743, 2026)：冻结 VLM 包 GeoGebra 约束引擎，Typed ToolSpecs，Propose-Draw-Verify，**每动作验证**(退化配置返 engine error 结构化回灌)。
  - **CADDesigner**(CAD 期刊 2026)：ReAct + ECIP 显式上下文 + 符号日志/视觉反馈迭代 + 成功案例知识库。
  - **cad-agents-platform**(GitHub 2026)：LangGraph 编排 + NX/SolidWorks/FreeCAD 各建 Agent(各自 validation) + 人在回路(interrupt/Command.resume) + AsyncPostgresSaver 检查点——架构与本项目的 harness+Checkpointer+Clarification 同构。
  - 微调先例：**CAD-Coder**(2025 微调 VLM 出 CAD 代码)；识别数据：**Sketch2CAD**(SIGGRAPH 2020)、**DeepCAD**(178k 构造序列数据集，可合成数据)。
- 本项目设计：SketchSpec(JSON 中间表示, id 稳定引用) → 确定性转译器(Spec→YH.SketchWorkPlane Python) → verify_sketch(读 RunSolve 后约束冲突/DOF/退化几何，有界重试)。与现有 Skill/ClarificationMiddleware/Checkpointer/长期记忆集成。
- 结论：业界共识=把"生成"与"正确性"解耦，验证分层(能跑+几何对)，API 知识用 RAG 不用微调。
- **决策(用户确认)**：不启动代码实现，等内核团队 API 文档冻结。原因：case-*.md 签名可能过期，且 verify_sketch 依赖的"读回"能力(DOF/冲突查询/RunSolve 异常语义/沙箱 doc 句柄)在现有文档完全缺失，基于假设写会返工。
- 已在 `docs/sketch-transpile-verify-design.md` 新增 §5.1「前置依赖：需内核团队冻结的 API 文档清单」(阻塞项 A 运行时前提/B 求解器反馈语义/C 最终签名)，作为与同事对齐的文档交付验收单；文档冻结前只做：对齐会 + 内部冻结 SketchSpec JSON Schema + 规划浅层验证兜底。
