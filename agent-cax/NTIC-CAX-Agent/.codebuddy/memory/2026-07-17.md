## Skill 机制（2026-07-17，已读源码确认）
- 定义：`skills/{public|custom}/<name>/SKILL.md` 目录 = 给 Agent 的领域操作手册（SOP）。frontmatter: name/description/license/allowed-tools；正文是 LLM 读的操作流程。public 只读，custom 用户可编辑。
- 触发机制两种（都有源码）：
  1. 被动注入：构建 Agent 时 `prompt.py` 把 enabled skills 列进 system prompt（带 container 路径），LLM 按语义自选。对应时序图 m3「已注入 sketch 技能」。
  2. 显式 slash 激活：用户消息 `/skill-name task` → 中间件#9 `SkillActivationMiddleware`（`agents/middlewares/skill_activation_middleware.py`）解析→读完整 SKILL.md→作为隐藏当前轮上下文注入（hide_from_ui=True）→记录审计事件（skill名/路径/sha256）。强制这一轮遵循。
- 安全：`allowed-tools` 在激活时经 `filter_tools_by_skill_allowed_tools` 过滤工具集，只放开 skill 声明工具；`scan_skill_content` 拦截危险内容。
- 执行：SKILL.md 只写调什么 API/顺序；真正执行=Agent 生成 Python→write_file 落盘→bash 沙箱跑→import YH 调 NCTI 内核（串起时序图 9→11 步）。

## 关键架构发现：DOE 业务层是主运行链路的 fork 副本（技术债）
- 主运行路由：`app/gateway/routers/thread_runs.py`（单数 thread），含 create_run/stream_run/list_runs/get_run。
- DOE 路由：`app/gateway/routers/threads_runs_doe.py`（复数 threads），仅重写了 `stream_run`，几乎逐行复制主 `stream_run`，差异只有：prefix `/api/threads_doe`、请求体 `RunCreateRequestDoe`（多一个 user_id 字段）、调用 `services_doe.start_run`、Content-Location 路径。
- DOE 服务：`services_doe.py`(8KB) fork 自 `services.py`(25KB)，只为注入 `user_id` 归属。
- 结论：双代码路径需同步维护，是项目最脆弱的定制点；正确重构方向是把 owner/user 归属下沉为 RunContext 一等字段（deps.py 已有 `RunContext`），合并 services_doe 进 services，删掉独立 DOE 路由。
- 用户目标：秋招投递 agent 岗位，希望做能体现项目理解、有竞争力的改进。建议方向 = 重构 DOE fork + 补 agent 评估(eval)/可观测层。
