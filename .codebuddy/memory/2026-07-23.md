## YHCADSmartCleaner Phase 0 spike 进展（NCTI 无头可行性）
- 用 wygcleaner 环境（Python，SDK 在 `YHCADSmartCleaner/SDK`）跑 `spike_headless.py`。
- **v1 结论**：步骤 1/2 OK（NCTI.Init + Document() 在 `geom` 级 DLL 无头可加载，地基没问题）；但 `doc.Open(stp)` 在无头**挂起/卡死**（输出停在步骤 2）。原因：doc.Open 内部要建视图/窗口子系统（open_ncti_file.py 里 doc.Open 后紧跟 `NCTI.View(doc.ID).CreateWindow(hwnd)`）。
- **v2 修正**：给 doc.Open 加 30s 守护线程超时；主导入路径改为 `doc.New("OCC","DCM",0)` + `doc.RunCommand("cmd_ncti_import_file", stp, name)`（与 `utils/through_step/_unit_test.py` 一致）。直接验证 RunCommand 在无头是否可用，决定架构 A/B。
- 决定性判据：RunCommand 导入若 EXECUTED → 架构 A（无头直跑）可行；若 NO-OP → 必须架构 B（宿主 NCTI 进程 / HTTP 微服务）。脚本已重写待用户重跑。
- 兼容性坑：`doc.AllNames()` 空文档返回 None（非 []），脚本统一 `or []`。
- 关键 API：纯内核识别 `doc.FindAllFaces(obj)` / `doc.FindFillets(sel.ObjectNames, min, max, type=0)` 不依赖 RunCommand；清理/导出只走 RunCommand（`cmd_ncti_remove_features` / `cmd_ncti_export_file`）。
- **v2 仍卡死根因**：doc.Open 在 NCTI C 扩展里阻塞且**不释放 GIL** → 守护线程的 30s `join` 超时无法让主线程恢复，整解释器焊死。线程超时救不了 GIL 死锁。结论：doc.Open 无头不可用（与 open_ncti_file.py 中 doc.Open 后必接 `NCTI.View(doc.ID).CreateWindow(hwnd)` 一致）。
- **v3 方案**：移除 doc.Open 探测；主导入路径改 `doc.New("OCC","DCM",0)`+`RunCommand(cmd_ncti_import_file,...)`；整段逻辑跑在「子进程 + 90s 硬超时」看门狗内（外层 `subprocess.Popen` + `p.wait(timeout=90)`，超时 `p.kill()`），挂起即 kill，绝不卡用户终端。决定性判据：RunCommand 导入 EXECUTED→架构A；NO-OP/超时→架构B。待用户重跑。

## v3 实测结果（重大修正！）—— 架构 A 可行
- **RunCommand 在无头可用**（推翻 sketch/kernel.py "RunCommand 是 no-op" 的结论；可能 sketch 测的是草图 solve 类命令 / 不同 DLL 组合）。实测：`cmd_ncti_import_file` 打印 `Imoprt file:288.265000 ms` 且成功加载；`FindAllFaces`+`FindFillets` 识别成功；`cmd_ncti_export_file` 成功。
- 步骤 5 初版 FAIL 是**探针写错**（传 `[-999]` 非法 cell id），NCTI 实际派发了命令但 -999 不存在→`invalid arguments`→锁命令系统要求 `doc.ResetCaseResult()`。非能力问题。
- 末尾 `0xC0000005` 崩溃 = NCTI 进程**拆卸段错误**，由坏状态触发；`_unit_test.py` 末尾用 `os._exit(0)` 跳过拆卸规避 → 我也在 spike 末尾加 `os._exit(0)`。
- **关键使用约束（写 Phase 1 必须遵守）**：① 每次 `doc.RunCommand` 前须 `doc.ResetCaseResult()`；② 清理入参必须是真实存在的 cell id（来自 FindFillets）；③ 返回值可能是 PyCapsule，需强转 bool 再存/判；④ 进程结束用 `os._exit(0)` 规避拆卸崩溃。
- **结论**：导入→识别→清理→导出整条链路在独立 Python 进程（wygcleaner + geom DLL）无头直跑可行 → **架构 A 成立**，无需宿主 NCTI 进程。下一步进入 Phase 1：在 NTIC-CAX-Agent 建 `app/cad_feature/` 工具层（`recognize_cad_features` / `clean_cad_features`），封装上述约束。

## M1 recognize 实测 + 修复两个 bug（2026-07-23 下午）
实测命令（wygcleaner Python 3.11.15，测试 STP = `D:\wyg\data\含倒角、圆角、通孔、盲孔(单solid).stp`）发现并修复两个 bug：

1. **bug 1：`load_ncti_geom()` 相对路径基准错误** → `ModuleNotFoundError: No module named 'ncti_python'`。
   - 根因：`system_config.json` 的 `dllPath: "../SDK"` 是**相对 config/ 目录**的（与 `config/config_load.py` 一致，后者用 `__file__` 取 config/ 作基准）。但 `recognition_cli.py` 在工程根，原代码用 `_THIS`（工程根）作基准解析，`../SDK` 被错解到 `xuntuiyitihua/SDK`（上一级），导致 sys.path 没加到真正的 SDK 目录。
   - 修复：`recognition_cli.py` 新增 `_CONFIG_DIR = os.path.join(_THIS, "config")`，`load_ncti_geom()` 解析相对路径时以 `_CONFIG_DIR` 为基准（`sdk = os.path.normpath(os.path.join(_CONFIG_DIR, sdk))`），与 `config_load.py` 对齐。
2. **bug 2：几何采样法识别漏检（0 个圆角）** → `features: []`。
   - 根因：原 `_recognize_fillet_geometry` 复刻 `on_find_fillet.py::find_fillet_by_geo`（FindAllFaces + 逐面 get_face_sample + is_constant_radius_fillet_by_points_and_normals 判定），对采样点/法向量判定阈值敏感，真圆角被判成非圆角。而 spike v4 用的内核原生 `doc.FindFillets(sel.ObjectNames, min, max, type)` 直接返回圆角 cell，更准更快。
   - 修复：① 新增 `_recognize_fillet_by_kernel`（走 `doc.FindFillets`，对每个 cell 二次 get_face_sample 补半径，采样失败半径置 null 不影响识别）；② method 语义调整：`ai/hybrid` → 走内核 FindFillets（推荐），`geometry` → 保留原逐面采样法作 fallback；③ CLI 默认 method 从 `geometry` 改为 `ai`。
- **实测结果（修复后）**：`recognize --stp 含倒角、圆角、通孔、盲孔(单solid).stp --type fillet --out r.json`，EXITCODE=0，识别到 **63 个圆角**（cell_id 0~135 分布），4 个成功采样出半径（约 3.0），其余 radius=null（采样补半径失败但识别本身正确），confidence=1.0。
- **PowerShell 引号坑**：`--params '{"min_radius":0}'` 在 PowerShell 下单引号内的双引号会被吃掉，导致 JSON 解析失败。规避：不传 params（用默认 `{}`）或用 `'{""min_radius"":0}'` 双引号转义。后端 runner.py 是 subprocess 调用，走 cmd 或 list 传参无此问题。
- 下一阶段：M1 clean 验证（清理这 63 个圆角导出 STEP）+ Phase 4（后端单测 + 文档）。

## M1 clean 实测 + 修复 bug 3（2026-07-23 下午）
实测命令 `python recognition_cli.py clean --stp <原.stp> --recognition r.json --out part_cleaned.step` 发现并修复 bug 3：
- **bug 3：clean 导入名与 recognition 不一致** → 63 个圆角全部移除失败，报 `"recognize_target" variable name does not exist`。
  - 根因：`run_recognize` 导入用硬编码 `"recognize_target"`，recognition JSON 记录的 object_name 全是 `recognize_target`；但 `run_clean` 重新导入时用了**不同的**硬编码 `"clean_target"`，于是 `cmd_ncti_remove_features("recognize_target",[cid])` 在文档里找不到该对象（文档里只有 `clean_target`）。
  - 修复：`run_clean` 从 recognition features[0].object_name 取导入名（与识别一致），不再硬编码；export_obj 改用导入后 `doc.AllNames()[0]`（实际对象名，更稳）。
- **实测结果（修复后）**：`removed_count: 45`（63 个圆角成功移除 45 个，18 个报 `geometry function error`——删除顺序导致的拓扑依赖：删前面圆角后后面依赖它的 cell 失效，属 NCTI 特性可接受），`file_exists: true`，STEP 文件 `part_cleaned.step` 551404 字节（原 STP 589179 字节，变小 ~38KB 合理）。
- **结论**：M1 recognize + clean 双链路实测通过，整个 CLI 可用。导入名必须在 recognize/clean 间保持一致（cell_id 依赖导入名+顺序）。
