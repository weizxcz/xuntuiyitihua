## 生成 graph 崩溃（退出码 3221225477=0xC0000005 访问冲突）日志可见性修复
- 现象：点"生成graph"后子进程崩溃，状态栏报"退出码 3221225477"，但业务日志 `run_xxx.log` 无报错（日志只到 INFO，停在 test 数据集处理中）。
- 根因：3221225477=0xC0000005 是 Windows **访问冲突/段错误**，发生在 C 层（NCTI DLL 或子进程 C 扩展），Python `try/except` 抓不到，业务日志来不及写；子进程 stderr 实际重定向到了 `work_dir/_subprocess_graph.log`（train_client.launch_subprocess 的 `stderr=subprocess.STDOUT`），但 `_finish_train_job` 失败分支只报了裸退出码、没把该日志尾部读出来。
- 改进（两文件）：
  - `ai/train_worker.py` 顶部加 `import faulthandler; faulthandler.enable()` —— C 层崩溃时把 Python 堆栈 dump 到 stderr（即 `_subprocess_graph.log`），可看出崩在哪个调用。
  - `function/on_train.py` 新增 `_describe_retcode`（退出码→可读含义，含 0xC0000005 等）、`_tail_lines`（读日志末 N 行）；`_finish_train_job` 失败分支改为：解析退出码含义 + 读 `_subprocess_graph.log` 尾部 + 把"失败摘要+子进程输出尾部"append 进业务日志（run_xxx.log），状态栏也提示日志路径。
- 注意：本次只让错误信息可见，**未修复崩溃本身**。崩溃根因（某 step 文件 / 环境-DLL 不兼容等）需重跑后看业务日志末尾的 faulthandler 堆栈或 `_subprocess_graph.log` 定位。

## 训练神经网络退出码 -1（日志空白）可诊性修复
- 现象：同事用同样数据集点"训练神经网络"，状态栏显示退出码 **-1**，业务日志和 `_subprocess_train.log` 均无报错信息。
- 根因分析：`-1` 在 Windows `subprocess` 上代表**进程被外部终止**（TerminateProcess）——常见为系统 OOM 杀进程 / 手动取消 / `multiprocessing`(spawn) Pool 子进程崩溃导致主进程异常退出；而 `train_worker.py` 原 `if __name__=="__main__"` 只 `except Exception`，不捕获 `BaseException`（SystemExit/信号/kill），且 Pool 工作进程的 traceback 不会冒泡到主进程 stderr，于是日志全空。
- 改进（两文件）：
  - `ai/train_worker.py`：入口 `except Exception` 改为 `except BaseException`（覆盖信号/SystemExit/子进程冒泡异常）；`main()` 内 `multiprocessing.set_start_method("spawn", force=True)`（Windows spawn 下 Pool 子进程异常会沿调用栈冒泡回主进程，配合顶部 `faulthandler.enable()` 把堆栈打印到 stderr 即 `_subprocess_train.log`）。
  - `function/on_train.py`：`_describe_retcode` 增加 `-1` → "被外部终止(可能 OOM/手动取消/子进程崩溃)"；`_finish_train_job` 失败分支兜底：若 `real_log_path` 缺失（崩溃在 setup_logging 前）或 stderr_tail 为空，把错误摘要 append 进 `stdout_log`(`_subprocess_train.log`)，保证至少一处日志有内容，状态栏提示写入路径。
- 结论：本次只增强可诊性。**-1 的真实诱因（OOM? 取消? 子进程崩溃?）需同事重跑后看 `_subprocess_train.log` 末尾的 traceback 或任务管理器内存占用**确认。

## 子进程运行逻辑重构（句柄/实时性/正确性）
- 目标：捋顺 train_worker / train_client / on_train 三处子进程逻辑，消除资源泄漏、提升代码优雅度与正确性。
- 先排查训练包 `ai/AAGNet_train/`：`step2graph_ncti.py` 等用 `with Pool(...) as pool:` 上下文管理器（自动 close/join/terminate），**Pool 进程资源本身已正确管理，无泄漏**，故焦点在主进程侧。
- 改动：
  1. `ai/train_client.py`：`launch_subprocess` 改为 `with`-等价地在 `Popen` 后立即 `log_fd.close()`（Windows 上子进程持有独立继承句柄副本，主进程关闭不影响写入），**消除主进程在整个训练期长期持有文件句柄的泄漏**；`[python_exe, "-u", "-m", ...]` 加 `-u` 强制子进程 stdout/stderr 无缓冲，**修复日志实时性差（原全缓冲 8KB 才 flush）**；返回由 3 元组改为 `(proc, stdout_log_path)` 二元组。
  2. `function/on_train.py`：`_launch_job` 适配二元组、`job` 字典移除冗余 `log_fd` 字段；`_finish_train_job` 删除已无用的 `log_fd.close()`；`_read_log_tail` 由文本模式 seek 改为**二进制模式**做增量定位（字节偏移永远合法），**修复中文 UTF-8 日志在字符中间 seek 抛 `ValueError`（原 `except OSError` 捕获不到会导致轮询崩溃）的隐患**；同步修正模块 docstring 过时描述（"跑在 Geo-Rec 训练管线"→ 已移植到 `ai/AAGNet_train`）。
  3. `ai/train_worker.py`：修正上一轮遗留的误导性 `error_callback` 注释，准确描述 spawn + BaseException + faulthandler 的崩溃可见性机制（Pool 在训练包内部 `with` 管理，外层控制不到 error_callback）。
- 三文件 lint 全过。**已补"程序退出时清理孤儿子进程"增强**（原待办）：`ai/train_client.py` 新增 `terminate_process_tree(proc)`，用 `taskkill /T /F /PID`（Windows）/ `os.killpg`（POSIX）杀整棵进程树——关键点：仅 `proc.kill()` 只能杀训练主进程，spawn 出来的 Pool worker 会残留成孤儿继续占 GPU/内存，必须按树杀；`main.py` 的 `wx.App()` 换成自定义 `CAEPlatformApp(wx.App)` 子类并重写 `OnExit`，退出时若 `frame.train_job` 仍非 None 则调 `terminate_process_tree(job["proc"])` 清理。两文件 lint 通过。
- 已知未决：当前**无中途取消训练的机制**（代码无 kill 子进程入口），用户若希望可中途停止，需另加取消按钮 + `proc.kill()`（建议配 `CREATE_NEW_PROCESS_GROUP` 以便整组终止 Pool 子进程）。

## 训练退出码 1 根因（graph/split 中文路径 GBK 解码）+ 写端编码闭环核查
- 现象（用户贴状态栏）：点"训练神经网络"失败，退出码 **1 (0x00000001)**，日志路径 `...\logs\沉头孔\run_xxx.log`。
- 真因：`base_functions.load_split_filelist` 读 split txt（`train.txt` 等，含中文"沉头孔"路径）未指定编码，Windows 默认 GBK 去解 UTF-8 字节序列 → `UnicodeDecodeError: 'gbk' codec can't decode byte 0xa4`。这是 Linux→Windows 移植默认编码坑。
- 已修读端编码（utf-8）共 7+ 处：`base_functions.py`（`load_split_filelist` 4 处 split 读取 + `load_json` + `load_json_or_pkl` 的 json 分支）、`data_utils/aagnet_dataloader.py`（2 处 label json）、`data_utils/aagnet_dataloader_base.py`（1 处 single_graph graph json）。
- **写端编码闭环核查（本轮）**：`step2graph_ncti.py` 生成 graph json 走 `base_functions.save_json_data`，原实现 `open(pathname,'w',encoding='utf8')` + `ensure_ascii=False` —— 已与读端 `load_json` 的 `utf-8` 等价，不会在另一处再炸。为彻底消除"utf8 vs utf-8"写法不一致疑虑，已把写端统一改为 `encoding='utf-8'` 并加注释说明读写两端编码必须一致（含中文落盘需 utf-8 + ensure_ascii=False 闭环）。graph json 文件名用 `step_path.stem`（基本名，不含中文路径），graph 内容存数值属性无中文，故"沉头孔"中文只会出现在 split txt，该路径已修好。
- 结论：读写两端编码现已**完全一致（均为 utf-8 + ensure_ascii=False）**，退出码 1 的根因链路已闭环。
